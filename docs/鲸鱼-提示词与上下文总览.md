# 鲸鱼 提示词与上下文总览（截至 0.2.1-alpha.1 第 68 轮 · 角色卡引擎 E1＋E2）

> 用途：**改提示词、改上下文装配、查"某句话到底有没有发出去"之前，先读这一份**。
> 这里只讲"每一轮请求实际发出去什么、从哪来、为什么这么排"，以及踩过的坑与实测数据；
> 代码结构与存储布局见 `docs/鲸鱼-代码结构总览.md`。
> **本文件是唯一需要随提示词改动同步更新的说明文档**（改了装配顺序/口径就回来改这里）。

## 一、一次聊天请求的完整结构

入口：`AiClient.chatStream(...)`（`data/AiClient.kt`），被 `ChatScreen.requestReply()` 调用。
真正的行数不多，但"什么放在哪"是这个项目里最容易出错的地方：

```
messages = [
  ① system  ← buildSystemPrompt(card, settings, userSetting, styleHint, memory, summary)
              （1 条，含视角约定 / 角色设定 / 世界观 / 用户设定 / 前情提要 / 共同记忆 / 补充要求 / 【叙事风格】）
  ② 历史    ← requestHistory(history, settings) 裁剪后的会话消息（scene 卡不在其中）
  ③ 尾注    ← tailHint 追加在**最后一条 user 消息**末尾（本轮硬性要求 + 单条特别指示）
              （历史里没有 user 消息时才退化成末尾一条 system 消息）
]
```

请求参数（都由 `data/ProviderProfiles.kt` 的供应商画像决定要不要发、发什么）：

| 参数 | 规则 |
|---|---|
| `model` | `settings.chatModel`；旧名 `deepseek-chat`/`deepseek-reasoner` 静默映射到 `deepseek-flash` |
| `temperature` | 画像声明支持的才发；值统一规范到 0.00–2.00 且**最多两位小数**（智谱会校验小数位，Float→Double 的精度残渣会导致 400） |
| `max_tokens` | `ProviderProfiles.effectiveMaxTokens`：配置值 ≥8192 时用它；判定为"在思考"时抬到 8192，否则用配置值 |
| `stream` | 恒为 `true`（真流式，P1-3；`chatCompletion` 那条路是 `false`） |
| 思考参数 | 按画像映射成 `thinking{type}` / `enable_thinking` / `reasoning_effort` 三套写法；`chatThinking` 为空则**不发**（用模型默认） |
| `reasoning_split` | 只有 MiniMax 一家要发：不传的话思考会被 `<think>` 包着混进正文（见 [[whale-thinking-leak-0-1-3]]） |

**核心纪律（贯穿全文）**：每轮请求都会重发**全部**上下文，费用 ≈ 请求次数 × 上下文长度。
所以本项目反复出现两条纪律：**空轴不注入**（没有内容的段落一个字都不发）、**每句话都要有存在的理由**。

## 二、系统提示词：段落与顺序（`buildSystemPrompt`）

**装配模式**（2026-09-22 起，`PromptMode`）决定开头与各块括注，中间资料块共用一套：

| 模式 | 用在 | 开头 |
|---|---|---|
| `RP` | 角色扮演（默认） | 扮演头 + 【视角约定（必须遵守）】5 条 |
| `SUGGEST` | 灵感回复（第五节） | "本次任务**不扮演任何角色**…替用户代笔" |
| `TOOL` | 工具形态（E4，界面入口随 E4） | "你是**任务处理工具**，不是在扮演中的角色" + 【任务契约】4 条 |

顺序固定，**前四段是"地基"，不要随意调换或删除**（RP 模式）：

| # | 段落 | 何时出现 | 为什么这么写 |
|---|---|---|---|
| 1 | 扮演头 + 【视角约定（必须遵守）】5 条 | 除灵感回复外恒有 | 角色卡的「世界观 / 当前场景」是用**角色的第一人称**写的（"我是一个穿越者"），不写死"这里的我 = 角色本人"，模型会把角色身份扣到用户头上。5 条分别是：①资料里的「我」= 角色；②用户只等于用户、不许替用户编身份；③「我/你」指代不混用；④始终以角色第一人称、不替用户说话、结尾留钩子、**长度默认贴合对话但【叙事风格】优先**；⑤排版（对白不加引号、动作用（）括注、不要 markdown 列表标题）。 |
| 2 | 【角色设定】 | 见下方"分层 or 老口径" | 角色人设 |
| 3 | 【世界观 / 当前场景】 | `card.scenario` 非空 | **场景卡不进历史消息**（`trimHistory` 过滤 `role == "scene"`），世界观只从系统提示词进来，避免每轮重复一份 |
| 3.5 | 【对话示例】 | `card.mesExample` 非空（E2 新增） | 语气/节奏示范。**必须声明"其中的情节没有发生过"**，否则模型会把示例当剧情接着往下写 |
| 4 | 【用户的设定】 | RP 恒有 | 空时必须显式说"用户没给设定"，否则模型会自己给用户编身份。来源是**会话级**的 `conversation.userSetting`（「本会话设定」弹窗里选）。⚠ **工具形态不注入这一段**（会把任务素材误读成交互关系设定） |
| 5 | 【前情提要】 | `conversation.summary` 非空 | 长期上下文，见第六节 |
| 6 | 【共同记忆】 | `conversation.memory` 非空 | 长期上下文，见第六节 |
| 7 | 【补充要求】 | `settings.extraSystemPrompt` 非空 | **全局**自定义提示词（设置页），所有会话共用 |
| 8 | 【叙事风格】+ 风格提醒 | 风格非全默认时 | 见第四节。**放在系统提示词最末**（第 9 轮调的），取近因 |

### 角色设定：分层 or 老口径（E1＋E2，2026-09-22）

判据是 `CharacterCard.hasLayeredPersona()`——`description` / `personality` / `mesExample`
**任一非空**就走分层，全空才把合并块 `persona` 整块注入：

| 情形 | 注入 |
|---|---|
| `description` / `personality` 有值 | 【角色设定】下分 **【角色描述】** 与 **【性格特点】** 两个小标题（分开写：描述管事实、性格管气质，揉一起会互相复读） |
| 三个新字段全空（**库里已有的老卡**） | 【角色设定】+ `persona` 整块照旧，**行为与本轮之前完全一致** |

⚠ **不做正则反向拆**：老卡的 `persona` 是当年导入时拼好的整块文本（含我们加的【背景故事】小标题），
用户手改过就拆坏了。所以口径是"**不拆，整块照旧注入**"，而不是"解析回三个字段"（第 66 轮定稿）。

⚠ **导出时的兼容副本要在导入时认出来**：老卡的 `persona` 会被抄进标准字段 `description`
（为的是别的应用能读到人设）。导入时若 `extensions.whale.persona` 与 `description` **逐字相同**，
就认定那是副本、丢掉 `description`——否则老卡"导出再导入"会凭空长出分层字段，口径悄悄从老式变分层。

### 宏（E2，2026-09-22）

`AiClient.expandMacros(text, card)`：`{{char}}` → 角色名、`{{user}}` → 「你」、`<BOT>` → 角色名。
**只作用在卡里读出来的文本上**（description / personality / mesExample / scenario / persona / taskBrief / outputFormat
以及开场白与场景卡），用户自己写的东西（本会话设定 / 补充要求 / 记忆 / 前情）**不展开**——那是人话，不是模板。
`{{original}}`（只对卡自带 system_prompt 有意义，而它**不注入**）与 `{{description}}` 这类自引用宏**一概不实现**：
支持一半比不支持更让人困惑，遇到不认识的宏原样留着，作者一眼能看出哪句没展开。
替换一律用 `Regex.replace` 的 **lambda 形式**——卡名里带 `$` 是合法输入，字符串形式会被当成组引用。

### 不注入的字段（保真但不影响对话）

`system_prompt`（调研结论：卡里的 system_prompt 应留空，避免与 App 拼装冲突；我们**只保存与导出**）、
`creator_notes` / `creator` / `character_version`（规范明确禁止用于提示词工程，只做展示）。
`post_history_instructions` **要注入，但不在系统提示词里**——见第三节。


### ⚠️ 最重要的一条实测结论：位置决定遵循度

**2026-09-16 真 key 实测**（doubao-seed-character，同一段真实历史，要求"篇幅=丰沛 单条 250~500 字"）：

| 同一段文字放哪 | 回复字数 | 达标 |
|---|---|---|
| 系统提示词最末 | 85~131（9 次） | 0/9 |
| **最后一条 user 消息末尾** | 250~300 | 3/5 |

原因：系统提示词在上下文**最前面**，后面还压着几十条历史（角色清一色短回复），
近因全在历史那边，**写在系统提示词里的"这一条必须怎样"几乎不生效**。
所以本项目的规矩是：

- **长期背景**（人设、世界观、用户设定、记忆、风格约定、视角边界）→ 系统提示词；
- **"这一条必须怎样"**（篇幅指标、单条特别指示）→ `tailHint`，贴到最后一条用户消息末尾。

顺带的收益：系统提示词变成**纯静态前缀**，对供应商的前缀缓存友好（换了风格才会变一次）。

## 三、本轮指令：`tailHint`（贴到最后一条用户消息末尾）

`ChatScreen.tailHint(style)` 组装，由 `AiClient.withTailHint()` 追加（带图消息是"文字+图片"数组，追加到文字部分）。
三段内容（**顺序即优先级**，越靠后越贴生成点）：

0. **角色后置指令** `card.postHistory`（v2 `post_history_instructions`，E2 新增）：排在最前，
   因为是**长期**要求（作者设定的始终遵守的规则），而下面两段是"这一条"的事。
   括注里写明"与视角边界冲突时以视角边界为准"——别人的卡不一定知道我们有视角约定。
1. **硬性要求** = `NarrativeStyles.hardReminder(style)`：
   `【本条硬性要求】按「慢镜头 · 丰沛 · 文学书面」写：单条必须写满 250~500 字，少于 250 字即不合格。`
   - 只有**带可核对指标**的档位才生成（当前只有"篇幅密度"两档：精简→"超过 80 字即不合格"、丰沛→"少于 250 字即不合格"）。
   - 为什么只给它："写得更文学"这种无处核对的形容词放末尾只是噪音；而字数模型能自查。
   - **反向不需要**：实测"精简 30~80 字"不加提醒也遵循（44 字，4/4 达标），所以只在"要写长"的方向补。
2. **单条临时导演**（`oneShotHint`，面板里那条"本轮特别指示"）：只作用下一条回复，不入库、不落盘；
   成功拿到正文后清空（空回复/出错时**保留**，用户重试就是想要同一条指令再生一次）。

## 四、叙事风格系统（`data/NarrativeStyles.kt` + `ui/screens/NarrativeStyleScreen.kt`）

**轴表是界面与 prompt 的唯一事实来源**：加一根轴、改一句文案只动 `NarrativeStyles.AXES`，两处界面与注入自动跟着变。

7 根轴（`value` 落盘，`hint` 注入 prompt，`enforce` 供 `tailHint` 用）：

| 轴 | 档位 | 备注 |
|---|---|---|
| 叙事节奏 `pacing` | 标准 / 快进 / 慢镜头 | 管事件推进，**不联动篇幅**（"快而不长"要能做到） |
| 篇幅密度 `density` | 标准 / 精简（30~80 字）/ 丰沛（250~500 字） | 唯一带 `enforce` 的轴；用户最常见的诉求 |
| 文笔语体 `prose` | 不指定 / 口语生活 / 文学书面 / 古风 / 电影分镜 / 剧本 | 只影响表达 |
| 情感基调 `moods` | 高甜 / 虐心 / 热血 / 悬疑 / 治愈 / 冷峻 / 搞笑（**多选，上限 2**） | 高甜 / 虐心 / 冷峻互斥；只着色，不改节奏篇幅与性格 |
| 角色主动性 `agency` | 被动应答 / 强导演 | 与地基第 4 条"结尾留钩子"对口 |
| 叙事视角 `pov` | 自由 / 第三人称贴身 | 选了非默认项时**本轴优先于地基的第一人称约定** |
| 时间处理 `timeFlow` | 蒙太奇 / 章节式 | 章节式要出小标题，而地基第 5 条禁标题 → 档位 hint 里自带"这是排版例外"声明 |

注入规则（`buildHint`）：

- **空轴不注入**；全默认时**整段【叙事风格】不出现**（一个字都不发）。
- 多选轴按**选择顺序**注入（不是表格顺序）——仲裁句"以最后选中的为准"只有最后一条真的排在最后才成立。
- 只开节奏+密度时补一句仲裁："节奏管推进、篇幅管字数：慢镜头+精简＝短句留白；快进+丰沛＝每句有新意。"
- **兜底句**（末句 `以上只调节表达方式，不改变前述视角约定与排版规则。`）：
  - 只在 `pov`/`timeFlow` 非空时用长版（"…的**其余部分**；上文另行指定的叙事视角与时间处理按其执行。"），其余保持短版。
  - **已实测证伪它不是"风格不生效"的元凶**（去掉它字数 85/111/120，与不去掉无差别），它承担"风格段不越权改视角/排版"的职责 ⇒ **别再动它**。
- **风格刚改过的一次性告知**（`ChatViewModel.styleNotice`，判断依据是**内存**里的 `lastSentStyle`，不落盘）：
  首次发送且风格非默认→`【风格提醒】严格按上面【叙事风格】的设置书写（档位名），不要沿用上文（含你自己历史回复）形成的篇幅与笔法习惯。`；
  风格刚改→`【风格刚修改】从本条起按新设置书写（…）`；风格被清回默认→`【风格已重置】…`。档位名由 `labelsOf()` 动态拼。

**字数预算**（改文案时的硬约束）：全 7 轴 + 双情绪取最长档 = **560 字**，加一次"风格刚修改"告知 = **616 字**。
交叉审阅定的纪律是 ≤400，已经超了 ⇒ **改叙事文案不许净增字数**，只许在档内替换（详见 [[whale-narrative-prompt-conflicts]]）。

## 五、灵感回复（`AiClient.suggestReplies`）：一条**独立**的请求

它是全项目唯一一条**不复用角色扮演系统提示词**的路。原因和踩过的坑：

- **它问的是"用户能说什么"**，不是"角色回什么"。所以：
  - 走 `buildSystemPrompt(..., forSuggestion = true)`：同样的资料块（角色设定 / 世界观 / 用户设定 / 前情 / 记忆 / 补充要求），
    但**开头换成"本次任务不扮演任何角色，你在替用户代笔"**，并且**去掉五条视角约定**、各块括注改成"「我」= 角色 / 「我」= 用户"。
  - **绝不注入【叙事风格】**（`styleHint` 不传）：强导演 / 第三人称贴身 / 文学书面 / 丰沛这些轴全是写给"角色"的，
    套到"用户该说什么"上会把灵感带成角色台词。风格参照改成**用户自己的历史发言**。
- **旧写法的教训**：原来是"角色扮演的系统提示词 + 末尾加一句'请暂时放下角色扮演（本任务优先于【视角约定】）'"。
  这两句正面对撞，模型二选一 → 间歇性把**角色的道具/伤势安到用户身上**（实测抓到"我攥着碎石…"＝角色刚扔的、"忍着肋骨疼"＝角色刚撞的）。
  也试过"只把任务段挪到末尾、保留角色扮演提示词"：6 次里 4 次模型直接开始**续写剧情**。⇒ 必须两处一起改。
- **任务段（`suggestionTask()`）放在最后一条用户消息里**，不是系统提示词：包含"禁止出现角色的台词/动作/神态/心理"、
  "照抄用户自己上一条发言的写法"、"**必须恰好 N 条**"、"每条 20~50 字"、"不要空（）"、"不要连成一段"、"只输出 JSON 字符串数组"。
- **任务段要写足，别精简**：实测压缩到 260 字后 12 次只有 5 次给足 3 条（长版 11/12）。
- **条数策略（2026-09-16 定）**：偶发少于三条就认，不要过多浪费 token ⇒
  只在结果 **0~1 条**时**补一次**请求，并把两次结果**合并去重**（不是整批替换）；2 条照收，不为凑数再发请求。
  补数请求失败用 `runCatching` 兜住，不连已经拿到的几条一起丢。首次约 82% 直接给足 3 条，属于可接受的偶发。
- **解析（`parseSuggestionList` / `finalizeSuggestions`）**：JSON 数组 → （失败）行解析 → 清洗（去空括注、把连出的括号压掉、压空白、去包裹引号）
  → 丢"客观离谱"的条目（>300 字，或同一字符连出 4 次以上；实测抓到过一次连吐上百个「（」的退化输出）
  → 去重 → 只剩 1 条且 ≥40 字时按「句末标点 +（」边界尝试拆开（模型常把 3 条连成一段）。
  **不拦**"只写动作没写台词"这类合法建议。
- **不落库、不进聊天记录**：点选一条只是**填进输入框**，不直接发送。
- **内存缓存与失效**：缓存按（会话 id + 角色 id + 消息条数）判定是否还有效，进度变了才重新生成；
  异步返回时会确认"用户还停在这个会话"才写入。

## 六、长期上下文：角色记忆与前情提要

两者都是**会话级**数据，都是**后台异步**生成、**按会话 id 写回**（动作期间用户可能切走，绝不能写进"当时看起来是当前"的会话）。

| | 【共同记忆】(`conversation.memory`) | 【前情提要】(`conversation.summary`) |
|---|---|---|
| 触发 | 每累计 **10 条**新消息（`messages.size ≥ memoryUntil + 10`） | 被裁掉且**尚未摘要**的消息 > 4 条（`prefixSize > summarizedUntil + 4`） |
| 取材 | `memoryUntil` 之后的最近 12 条，每条截 300 字，合计上限 5000 字 | 被裁掉的前缀，每条截 400 字，合计上限 6000 字 |
| 提示词要点 | "**不要**包含角色卡里已有的基础设定（人设/世界观/场景）——那些 AI 本来就知道，写进来纯属浪费"；删过时条目、合并重复、补新事实；要点式每行一条，**≤400 字** | 把【已有前情提要】与【新剧情片段】**合并**成一份：要点式、**≤300 字**、保留关键事件/关系变化/约定 |
| 参数 | `maxTokens = 1024`、**固定 thinking = off** | 同左 |
| 失败 | 静默（自动记忆失败不打扰用户） | 静默 |
| 手动编辑 | 「更多 → 角色记忆」编辑的是**同一份数据** | 无手动入口 |

**为什么这么设计**：长会话迟早撑爆上下文，与其把历史整段丢给模型"自己记"，不如让模型定期把要点压缩成一份
小而稳的事实清单。**记忆里不写角色卡已有的内容**是最省 token 的一条（那部分每轮都在系统提示词里）。

## 七、历史与图片的裁剪

`AiClient.requestHistory(history, settings)` 是**所有发送口**（聊天、灵感回复）的统一入口：

1. `trimHistory`：先取**最近 `settings.historyLimit` 条**（默认 40，设置页可调），
   **过滤掉 `role == "scene"`**（场景卡只走系统提示词）；再按**字符预算 24000** 从最早开始丢。
2. 一条消息的"字符当量" = 正文字数 + 随消息图片的 base64 体积，
   **单张图封顶 6000**：不封顶的话一张手机照片就能把整段文字历史一次挤光（图片曾经完全不计入预算，是个漏洞）。
3. `collapseToLatestImage`：**只吃一张图的模型**（`ModelCatalog.singleImageOnly`，如腾讯 HY-Vision）只保留**最近一张**图，
   其余带图消息退化成纯文本 —— 否则每轮把历史里每张图重新 base64 上传，请求体轻松上 MB。
4. 图片是否发送还取决于**当前模型能不能看图**（`ModelCatalog.isVisionModel`）：
   不是视觉模型时 `contentOf` 只发文字（避免白烧一份 base64 的输入 token，也让"模型答非所问"的原因可查）；
   图片读取失败会退化成纯文本并留一条 `Log.w("WhaleVision", …)`。

## 九、实测结论与"别再改"的清单

1. **位置 > 措辞**：同样的要求放系统提示词 vs 贴最后一条用户消息，达标率 0/9 对 3/5。改提示词先想"它离生成点有多远"。
2. **兜底句不是元凶**（去掉它 85/111/120，与不去掉无差别）⇒ **别再动它**。
3. **条数/篇幅这类要求要写足**：精简版任务段反而更差（5/12 对 11/12）。
4. **只在"要写长"的方向补硬指标**：精简档本来就遵循，别给它加噪音。
5. **快进不联动密度**：拆轴就是要让"快而不长"成立，组合语义交给套餐（极速爽文＝快进+精简、沉浸小说＝慢镜头+丰沛）。
6. **灵感回复绝不注入叙事风格**（会把用户台词写成角色台词）。
7. 验证 prompt 的手段：本机起 127.0.0.1 的转发代理打真接口做 A/B 对比（聊天与灵感回复各一组；调试包允许回环 http）。
   切之前先 force-stop 应用，否则内存里的旧设置会把配置文件覆盖回去；
   应用是"一家一份 Key"，回环地址要在 `providerKeys` 里挂一份原 Key 的密文。
